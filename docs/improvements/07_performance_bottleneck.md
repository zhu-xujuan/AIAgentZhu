# パフォーマンスボトルネック分析

## 概要

LLM有効時のベンチマークテスト（19ドキュメント、50質問）の結果から、システムのボトルネックを特定。

**テスト環境**:
- LLMモデル: qwen2.5:7b
- 合計処理時間: 1498秒（約25分）
- LLM呼び出し総数: 157回

---

## 1. 重要な発見: チャンク数

```
ドキュメント数: 19
チャンク総数:   19
チャンク/ドキュメント: 1.0
```

**全ドキュメントが1チャンクのみ**（テキストが800文字未満のため分割されない）

→ **チャンク並列処理は効果がない**

## 4. ボトルネックの真の原因

### 4.1 Extract（ファクト抽出）が最大のボトルネック

**原因**:
1. **出力が複雑**: 複数のファクトをJSON構造で生成（5-7個/ドキュメント）
2. **入力トークンが多い**: チャンクテキスト + 詳細な指示
3. **推論が重い**: 文脈理解 + 構造化出力の生成

**タイムアウト発生ケース**:
| ドキュメント | 処理時間 | タイムアウト |
|------------|---------|-------------|
| report_annual_2023.txt | 180秒 | 3回 |
| meeting_minutes_global.txt | 179秒 | 2回 |

### 4.2 現在の処理フロー（逐次処理）

```
現在の処理:

Doc1 ──[classify]──[extract]──[quality]──→
                                          Doc2 ──[classify]──[extract]──[quality]──→
                                                                                    Doc3 ...

Q1 ──[parse]──[format]──→
                         Q2 ──[parse]──[format]──→
                                                  Q3 ...

問題: 全てが直列実行 → LLMの待ち時間が累積
```

## 5. 正しい改善策

### 優先度: 高

#### 5.1 ドキュメント並列処理（最も効果的）

```
現在（逐次）:
Doc1 → Doc2 → Doc3 → ... → Doc19
合計: 19 × 60秒 = 1140秒

改善後（並列）:
Doc1 ─┐
Doc2 ─┼→ 同時処理
Doc3 ─┘
...
合計: 60秒 × ceil(19/並列数)

並列数3の場合: 60秒 × 7 = 420秒（63%削減）
並列数5の場合: 60秒 × 4 = 240秒（79%削減）
```

**実装方法**:
```python
import asyncio

async def process_documents_parallel(documents, ollama_client, max_concurrent=3):
    semaphore = asyncio.Semaphore(max_concurrent)

    async def process_with_limit(doc):
        async with semaphore:
            return await process_document(doc, ollama_client)

    tasks = [process_with_limit(doc) for doc in documents]
    results = await asyncio.gather(*tasks)
    return results
```

**注意**: Ollamaの同時リクエスト制限を考慮（デフォルト: OLLAMA_NUM_PARALLEL=1）

#### 5.2 質問並列処理

```
現在（逐次）:
Q1 → Q2 → Q3 → ... → Q50
合計: 50 × 7秒 = 350秒

改善後（並列数5）:
合計: 7秒 × 10 = 70秒（80%削減）
```

#### 5.3 プロンプト最適化

```
現在のExtractプロンプト: ~1500トークン
最適化後: ~500トークン

方法:
- 不要な例を削除
- 指示を簡潔化
- Few-shotを1例に削減

期待効果: 30-40%の処理時間短縮
```

### 優先度: 中

#### 5.4 軽量モデルの使用

| モデル | サイズ | 予想速度 |
|-------|-------|---------|
| qwen2.5:7b（現在） | 7.6B | 基準（45秒/extract） |
| qwen2.5:3b | 3B | 2倍速（22秒/extract） |
| qwen2.5:1.5b | 1.5B | 3-4倍速（12秒/extract） |

**トレードオフ**: 精度低下の可能性あり

#### 5.5 処理の選択的スキップ

```
条件付きLLM使用:
- 短いドキュメント（<200文字） → ルールベースのみ
- 既知のパターン（請求書など） → テンプレート処理
- 重複ドキュメント → キャッシュから取得
```

#### 5.6 Ollama設定の最適化

```bash
# 並列処理を有効化
OLLAMA_NUM_PARALLEL=4

# GPUメモリ最適化
OLLAMA_GPU_LAYERS=35

# コンテキスト長を制限（メモリ節約）
OLLAMA_NUM_CTX=2048
```

### 優先度: 低

#### 5.7 バッチ処理（複数入力を1リクエスト）

```
現在:
classify(doc1) → classify(doc2) → classify(doc3)
3回のAPIコール

改善:
classify_batch([doc1, doc2, doc3])
1回のAPIコール

注意: Ollamaは標準でバッチ処理をサポートしていない
      → カスタム実装が必要
```

#### 5.8 キャッシュ機構

```python
import hashlib

def get_cached_or_process(doc, cache):
    doc_hash = hashlib.md5(doc['content'].encode()).hexdigest()

    if doc_hash in cache:
        return cache[doc_hash]

    result = process_document(doc)
    cache[doc_hash] = result
    return result
```

### 10.3 特定された問題点

- **期待**: 5万円

- **原因**: LLMが条件「世帯主の場合」を認識して情報を抽出できない
- **対策**: QAシステムプロンプトに条件付き質問への対応ヒントを追加

#### 問題3: 英語質問でのベクター検索失敗

  2. ハイブリッド検索（ベクター + 全文検索）を使用

### 10.6 改善内容の詳細（最終版）

**LLMによるクエリ拡張（汎用的アプローチ）**

ハードコードされた辞書ではなく、LLMを使用して質問を動的に拡張:

```python
# qa_agent.py
QUERY_EXPANSION_PROMPT = """以下の質問から、文書検索に使用するキーワードを抽出・生成してください。

## 質問
{question}

## タスク
1. 質問の意図を理解する
2. 重要なキーワードを抽出する
3. 曖昧な表現があれば、具体的な関連語に展開する
4. 英語の質問は日本語キーワードに変換する

キーワード:"""

async def expand_query_with_llm(question, ollama_client):
    # LLMでキーワードを生成
    result = await ollama_client.generate(prompt, system, temperature=0.1)
    keywords = [k.strip() for k in result.text.split(",")]
    return keywords
```

**動作例:**
- 「会社の規模」→ `従業員数, 資本金, 売上高, 企業規模`
- 「What is the password minimum length?」→ `パスワード, 最小, 文字数`
- 「世帯主の場合の住宅手当」→ `住宅手当, 世帯主, 福利厚生`

### 10.7 解決された課題（LLMクエリ拡張による）

すべての問題がLLMによる汎用的なクエリ拡張で解決:

| 問題 | 解決方法 |
|------|----------|
| 曖昧な質問（会社の規模） | LLMが「従業員数, 資本金, 売上高」に展開 |
| 英語質問 | LLMが日本語キーワードに変換 |
| 条件付き質問 | LLMが条件を含むキーワードを生成 |

**メリット:**
- ハードコード不要で保守性が高い
- 新しい質問パターンにも自動対応
- 多言語対応が容易

**トレードオフ:**
- 応答時間が約2秒増加（クエリ拡張のLLM呼び出し）

### 10.8 今後の改善候補

1. **クエリ拡張のキャッシュ**: 同一質問のキーワードをキャッシュして高速化
2. **軽量モデルの使用**: クエリ拡張専用に小さいモデルを使用

### 12.4 Cold Start問題の詳細

**Embedding生成**:
- 初回（Cold）: **60秒**（タイムアウト）
- ウォームアップ後: **0.02〜0.03秒**

**原因**: Ollamaがembeddingモデルを初回ロードする際の遅延

**解決策**: アプリ起動時にウォームアップ処理を実行

```python
@app.on_event("startup")
async def startup():
    # Embedding モデルをウォームアップ
    await ai_client.embed("warmup")
    logger.info("Embedding model warmed up")
```

### 12.5 LLM生成速度の測定

| 回答タイプ | 時間 | 出力長 | 速度 |
|-----------|------|--------|------|
| 短い回答 | 0.57s | 15 chars | 15.9 tok/s |
| 中程度 | 1.81s | 397 chars | 37.1 tok/s |
| 長い回答 | 25.41s | 5153 chars | 37.3 tok/s |

**特徴**:
